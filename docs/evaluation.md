# Evaluation methodology (v1.0)

This document fixes how invoice-pilot measures extraction accuracy and cost. It was
written and frozen **before the first live model run** (2026-10-24, task 08). Any change
to the rules below is a new version of this document, and every published number is
recomputed under the new version. The implementation lives in `eval/evalrun/`; each
rule and metric has a test in `tests/evalrun/`.

## Dataset

- `eval/dataset/`, version **1.0**, frozen 2026-10-24 (commit `080e17b`): **120 synthetic
  invoices** generated by `eval/evalgen/` with seed 20261023. No real documents or
  personal data are involved; names, addresses, identifiers and amounts are invented.
- Composition (`eval/dataset/manifest.json`): 48 text PDFs, 36 scanned PDFs (image only,
  no text layer), 36 photos (JPEG); 72 English and 48 German documents; 10 layout
  templates, 12 documents each; 8 two-page PDFs; currencies EUR, USD, GBP, CHF, JPY.
- 15 documents (12.5 %) are deliberately **corrupted**, two or more of each kind: total
  not equal to subtotal plus tax, a line amount not equal to quantity times unit price,
  subtotal not equal to the sum of lines, missing invoice number, IBAN with wrong check
  digits, due date before the invoice date, VAT ID of the wrong format. The manifest
  records the kind and the expected issue code of every corrupted document.
- Ground truth (`eval/dataset/ground_truth/<id>.json`) is **as printed**: a corrupted
  document is extracted correctly when the model returns the printed, wrong values. It
  is not the model's job to repair the document; that is what the deterministic checks
  are for.
- Validation runs with `today` = the dataset **reference date 2026-10-01** from the
  manifest, so date rules behave the same on every run.

## What is compared

The pipeline under test is `services.extraction.extract_invoice`: input preparation,
one model call (plus one retry on an unusable answer), strict parsing into the domain
`Invoice`, deterministic validation. Its output is compared with the ground-truth
invoice field by field.

### Normalization

Key fields are compared **exactly after canonicalization**:

| Field | Canonical form |
|---|---|
| `invoice_number` | trimmed, runs of whitespace collapsed to one space |
| `invoice_date`, `due_date` | calendar dates |
| `currency` | upper case |
| `subtotal`, `tax_rate`, `tax_amount`, `total` | `Decimal`, numeric equality (`19.9` equals `19.90`) |
| `iban` | `domain.normalize_iban` (upper case, no whitespace) |
| `supplier.tax_id`, `buyer.tax_id` | `domain.normalize_tax_id` (upper case; spaces, dots and hyphens removed; an EIN keeps its hyphen) |
| `bic` | upper case, no whitespace |
| `supplier.name`, `buyer.name` | trimmed, whitespace collapsed, case ignored |
| `line_items` | correct only if the number of lines equals the ground truth **and**, line by line in printed order, `quantity`, `unit_price` and `amount` are numerically equal |

Free-text fields are compared after a looser normalization (lower case, line breaks and
commas replaced by spaces, whitespace collapsed) and are reported **separately**; they
never enter the main metrics: `supplier.address`, `buyer.address` and
`line_items.description` (all descriptions, in order, with the same line count).

A `null` in the ground truth and a `null` in the answer match; a `null` against a value
is a mismatch. When extraction fails (no usable answer after the retry), every field
counts as wrong.

## Metrics

All metrics are computed per model configuration over the **evaluated** documents:
those with a verdict (`auto_approved` or `needs_review`). Documents without a verdict
are reported as counters and excluded from denominators: *missing recording* (replay
only) and *provider error* (the API failed after retries). Every ratio is reported with
its numerator and denominator.

1. **Field accuracy** - share of documents where the field is correct, for each key
   field and, separately, each free-text field.
2. **All key fields correct** - share of documents where every key field is correct.
   This is the "model only" number: the accuracy an automatic approver would have if
   it approved everything.
3. **Verdicts** - share of `auto_approved` and `needs_review` documents.
4. **Precision among auto-approved (main metric)** - among the documents the pipeline
   auto-approves, the share where every key field is correct. The denominator (number of
   auto-approved documents) is always shown next to it. This is the promise of the
   product: what is approved automatically is right.
5. **Corrupted documents caught** - share of the corrupted documents that received
   `needs_review`; separately, the share caught **with the expected issue code** among
   the reported issues.
6. **Clean documents sent to review** - share of clean documents that received
   `needs_review` (unnecessary manual work).
7. **Counters** - extraction failed (no usable answer after a retry), provider errors,
   model retries.
8. **Breakdowns** - metrics 2-6 by input type (text PDF, scan, photo) and by language.
9. **Model only vs model + checks** - metric 2 next to metric 4.

A corrupted document whose printed error the model silently "repairs" (for example, it
returns subtotal plus tax instead of the printed total) is auto-approved by the checks
but its `total` differs from the as-printed ground truth: it lowers the main metric and
the corrupted recall. This is intended.

## Cost

Cost is computed from the **actual usage** reported by the provider for each recorded
answer (input tokens; output tokens, which include thinking or reasoning tokens):

- mean and p95 (nearest rank) of input and output tokens per document, by input type;
- cost per document and per 1,000 documents at the list price **valid on the recording
  date** (`invoice_pilot.llm.pricing.cost_usd`), summarized as "1,000 invoices ~ $X on
  LLM calls" for the dataset mix (40 % text PDF, 30 % scan, 30 % photo).

Replay runs price the one recorded (successful) call per document. A live run that
needed a retry has paid for the failed attempt as well; `predictions.jsonl` of the live
run keeps every attempt, the recording keeps only the answer that was used.

## Runs and reproducibility

- Model answers are recorded once (`eval/recordings/<provider>/<model>/<key>.json`,
  key = document digest + provider + model + prompt version + schema digest + model
  parameters) and replayed afterwards; replay makes no network calls and needs no keys.
- `eval/run.py` writes, per configuration, `eval/results/<config>/predictions.jsonl`
  (one line per document: verdict, issue codes, per-field comparison, usage, cost),
  `metrics.json` and `summary.md`. The files are deterministic: sorted keys, LF line
  endings, and the run date is the date of the latest recording used, not the clock.
  Two replays of the same recordings produce byte-identical files.
- Configurations (`eval/evalrun/configs.py`): `gemini-flash-lite` (primary,
  `gemini-3.5-flash-lite`), `gemini-flash` (`gemini-3.8-flash`), `gpt-luna-auto` and
  `gpt-luna-low` (`gpt-6-luna` with image detail `auto` and `low`). Gemini runs at the
  lowest thinking level the model accepts and the API's default media resolution;
  OpenAI runs with reasoning effort `none` and nothing stored on the provider side.
- The prompt (`extraction-v1`) and the response schema are part of the recording key;
  changing either invalidates the recordings and starts a new measurement.

## Limitations

- The dataset is synthetic: one generator, ten layouts, two languages, invented
  companies. Real invoices are more varied (logos, stamps, handwriting, tables with
  discounts or several tax rates), so real-world accuracy will be lower than measured.
- Scans and photos are simulated distortions (noise, blur, rotation, lighting), not real
  camera captures.
- One tax rate per invoice; discounts, deposits and multi-currency documents are out of
  scope for v1.
- 15 corrupted documents of 7 kinds give coarse recall estimates; a single document is
  6.7 percentage points.
- Free-text fields are compared loosely and excluded from the main metric by design.
